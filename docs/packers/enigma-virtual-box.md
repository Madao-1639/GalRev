# Enigma Virtual Box（EVB）：第三方打包器

本文记录 Enigma Virtual Box 打包格式的容器结构，与具体引擎无关——它套在宿主程序外面，
和游戏本身用什么引擎没有关系。

**为什么记在这里**：很多民汉/移植补丁为了"单文件交付"，会把改动过的资源塞进一个新 exe
或一个外部 `.pck`。遇到这类产物时，先怀疑是 EVB，别急着按引擎的归档格式去解。

## 一、判定

两条互相独立的特征，任意命中一条就足够怀疑：

1. PE 节表最后两节叫 `.enigma1` / `.enigma2`（`Detect It Easy` 也按这个名字判）。
   注意 `.enigma1` 的 `SizeOfRawData` 常常远大于 `VirtualSize`——**文件系统就在这段"多出来"的
   原始数据里**，不要按虚拟大小去截断。
2. 文件里能搜到 `45 56 42 00`（`EVB\0`）。

## 二、两种载体

| 载体 | `EVB\0` 的位置 | 说明 |
|---|---|---|
| exe 内嵌 | `.enigma1` 段内某处 | 需在文件里搜魔数；后续所有偏移都相对文件开头 |
| 外部包（`.pck` 等） | 文件偏移 0 | 解析逻辑完全相同 |

判断方法：读前 4 字节，是 `EVB\0` 就是外部包（魔数偏移 = 0）；否则全文件搜。

## 三、节点表布局（PE-external 变体）

```
偏移 magic+0x00  EVB_PACK_HEADER   4s("EVB\0") + 60s
偏移 magic+0x40  EVB_NODE_MAIN     u32 size | 8s | u32 objects_count
之后逐节点（顺序 = 文件系统树的前序遍历）：
  EVB_HEADER_NODE   u32 size | 8s | u32 objects_count
  EVB_NODE_NAMED    u16 名（UTF-16LE，双 0 结尾）| u8 type
  type = 2（文件）  EVB_NODE_OPTIONAL_FILE
                      2s | u32 original_size | 4s | 8s×3（三个 FILETIME）| 15s | u32 stored_size
  type = 3（目录）  25 字节（时间等）
  type = 其他       视为结束
```

文件内容区起点：

```
content = magic + 0x40 + 16 + main.size - 12
```

文件按 `stored_size` **依次紧排**（没有每文件的填充）。目录 `%DEFAULT FOLDER%` 表示虚拟根，
拼路径时要折叠掉。

### 三个致命细节（都是实测踩出来的）

1. **主节点之后要回退 1 字节**才是第一个头节点的起点。参考实现
   （`evbunpack::pe_external_tree`）里就是一句 `fd.seek(-1, 1)`，看起来像笔误、其实是格式。
   不回退时下一个 u32 读成 0，**整棵树只解出主节点、文件数为 0，而且不会报错**——
   空包（宿主 exe 只有一个空虚拟根）也是这个表现，极易误判成"这个包本来就是空的"。
2. **节点 `offset` 是相对文件开头的绝对偏移**，因为 `content` 的计算里已经含了 `magic`。
   若把它当"相对魔数"再加一次 `magic`：外部包（magic = 0）完全看不出问题，**exe 内嵌时
   才会错**，症状是解出来的图魔数不对、或大文件只能读到一半（文件尾截断）。
3. **两个阵列/结构与长度相关**：节点名是双 0 结尾的 UTF-16LE（不能按单字节 C 串读），
   且读取循环要按 `objects_count` 递归展开目录，不能只平铺一层。

### 验证方法

跨载体各取一个真实包，**用全量哈希对拍**（与参考实现逐个文件比 sha256），不要抽查前几个：
第一个文件通常落在小偏移处，偏移错几十万字节也可能刚好切在某个文件中间而"看起来像正常数据"。

## 四、分块压缩（常见但已见的样本里没出现）

`stored_size != original_size` 的条目是 EVB 的"压缩模式"。布局：

```
EVB_CHUNK_BLOCK   u32 size（块长表总长）| 4s
块长表            u32 × n（每 3 个 u32 取第 1 个＝该块压缩后长度）
逐块数据          每块是裸 aPLib 流
```

实测数据点：接触过的 4 个真实包（663 个条目）与 `evbunpack` 自带 11 个测试包，
**压缩条目数全部为 0**——打包时勾选压缩的比例很低。

⇒ **建议不实现，遇到就抛异常**："该包用了分块压缩，需要 aPLib 解码器（未实现）"。
理由：没有真实样本可验证的解压器，解错了不会报错、会静默产出坏文件，比直接失败糟得多。
真要实现时，`evbunpack-rs` 的纯 Rust aPLib 实现可作参照，且**必须先用真实压缩包验证**。

## 五、包里的文本文件

EVB 包内的 `.tjs` / `.ks` / `.txt` 通常是 **UTF-16LE 明文**（BOM `FF FE` 开头），
与 krkr 归档里的 TVP 打散文本（`FE FE …`）是两回事——不要拿打散解码器去处理它们。

## 六、参考实现

- 上游：`mos9527/evbunpack`（Python，v0.2.6）⟶ 派生的 `evbunpack-rs`（Rust）。两者都需要 `aplib` 依赖；纯标准库重写时把那部分换成「报错」即可（见 §四）。
- 本知识库**不收 EVB 的实现代码**（它不是引擎能力，与 krkr/AdvHD/Willplus 库无关）；本文只记录格式与判据，便于按 §三 自行实现或用上游工具对拍。
