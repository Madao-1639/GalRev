# CMVS 引擎机制

## 1. 资源查找：引擎自带「外挂覆盖」槽位

启动脚本（`data/code/start.ps3`）在启动时把若干目录/封包挂进若干**路径表**，
每张表有固定槽位数；查找时**从槽 0 开始、首个命中即返回**。

表项结构 `[2048 字节路径][4 字节 pack 对象指针]`：路径以 `\` 结尾即**目录**
（直接开磁盘文件），否则是**封包**（走 pack 对象 vtable）。这由
`imul`, 偏移 `804h` 的寻址形态可辨认出来。

挂载命令走统一系统命令分发表，命令号形如 `0x2000 + N`；另外有一组 6 参数版本
（额外 4 个 CPZ 索引密钥字），用于需要解密的封包。

### 可外挂的两个槽

典型布局（跨作需重验，以 `start.ps3` 实际挂载序为准）：

| 资源族 | 槽 0 | 其余槽 |
|---|---|---|
| 脚本 | **`data\update\`** | `data\code\` |
| 图片 | **`data\image\update\`** | `data\image\chip\`、各 `*.cpz` |

**结论**：把 `*.ps3` 放进 `data/update/`、`*.pb3` 放进 `data/image/update/`，
就能覆盖 `data/code` 与各封包里的同名成员，**原生文件一个字节都不用改**。
多数作品的官方补丁就是靠这两个目录做覆盖的。

界面图是**扁平文件名**（`cg_bg.pb3`、`config02_chip.pb3`），即
`data/image/update/cg_bg.pb3` 能压过 `chip` 目录或封包里的同名片。

## 2. 系统命令分发表

脚本里的系统命令由一个跳转表分发：`case N` → 命令号 `0x2000 + N`。
挂载命令与其它系统命令在同一张表里，因此「找挂载序」= 反汇编 `start.ps3` +
对照这张表确认每个 case 的处理器。

> 跨作：表内 case 数量与处理器地址随构建变化。定位方法是从 `start.ps3` 的
> 挂载命令出发 xref 回分发表，而不是硬编码地址。

## 3. 不改 exe 的注入点：代理 DLL

CMVS 的 exe **静态导入** `mog3x32.dll`（Purple 的 OGG/MOG 音频封装库，体积约 300 KB，
仅依赖 KERNEL32）。它在游戏目录，Windows 与 Wine/Proton 都优先从 exe 所在目录加载。

做法：

1. 原文件改名（`mog3x32.dll` → `mog3x32.dll.orig`，**内容不变**）
2. 放同名代理：把原 DLL 的全部导出用裸 `jmp [ptr]` 转发过去，参数/返回值/调用约定全透传
3. 代理的 `DllMain(PROCESS_ATTACH)` 里做内存补丁与私有字体注册

好处：玩家直接从 Steam 启动原 exe（时长统计、云存档、成就全部正常）；无启动器 exe；
字体免安装；卸载 = 删文件 + 改回原名。

**为什么选它而不是别的 DLL**：

| 候选 | 为什么不选 |
|---|---|
| `dinput8` / `DSOUND` | 只在 `JOYPAD_USE` / 音频后端特定分支才 `LoadLibrary`，条件不可靠 |
| `version` / `winmm` / `gdi32` | 在 `KnownDLLs` 里，目录劫持无效 |
| `dxgi` / `d3d11` | Wine/Proton 下默认走 builtin，会被忽略 |

### DllMain 里不能直接 LoadLibrary 补丁本体

进程还在加载器临界区内，`LoadLibrary` 会被拒绝（`ERROR_INVALID_ADDRESS`）。
必须 `CreateThread` 开线程，等 `gdi32.dll` 出现在模块表、并再让出初始化阶段之后加载。

### 内存写入纪律

- 所有字节补丁**先校验期望字节再写**，不符则跳过并记日志，绝不盲写。
- 写入前 `VirtualProtect(PAGE_EXECUTE_READWRITE)`，**写完恢复原保护属性**
  （否则页面长期 RWX，是可被检测的特征）。
- 版本闸门：若一组关键补丁未全部命中，应该整体停用其余改动，让游戏按原版行为运行。

## 4. 音频：

`mog3x32.dll` 导出约 19 个符号（`MOG_Init/InputFile/GetPcmFormat/GetProcessFrame/Replay…`
与对应的 `MGV_*`），代理需要把它们**全部**转发，漏一个会在特定场景崩溃。

## 5. 随包字体的三条硬性要求

要让「游戏内字体列表能看到、设置界面显示的名字与实际渲染一致」，随包字体必须同时满足：

| 要求 | 原因 |
|---|---|
| **必须是 TrueType(glyf) 轮廓** | OTF(CFF) 字体在 `EnumFontFamiliesExA` 回调里 `fonttype=2`(DEVICE)；游戏列表只收 `fonttype=4`(TRUETYPE)，所以 OTF 永远不会出现在列表里。转换：`Cu2QuPen` + `TTGlyphPen` 转 glyf，并把 `sfntVersion` 改成 `\0\1\0\0` |
| **族名必须是目标编码的中文** | 字体名输入框跑在双字节排版模式下时，ASCII 族名会被两两配对成乱码，玩家选不中 |
| **显示名 = 实际用名** | 两者写成不同的串时，GDI 匹配不到字族会退回西文字体，整个文本对象变豆腐块 |

另外 `name` 表要**同时写 0x409 与 0x804 且内容相同**，否则中文系统取 0x804 记录、
英文系统取 0x409，名字会不一致。

**字重**：引擎通常只请求两个 weight（正文与粗体）。随包字体出两个 face（如 Medium 500 +
Bold 700）让 GDI 分别就近命中，避免合成加粗发毛。具体档位查 `.rdata` 里的字重表。

## 6. 改默认字体：改默认值，不要拦截读取

引擎的字体设置项**默认值写死在 exe 里**（作为 `GetPrivateProfileString` 的 `lpDefault` 参数），
配置文件里通常根本没有这一项。

- ❌ 不要加 `GetPrivateProfileString` 钩子「读到旧值就换成我们的」——那等于废掉玩家的选择：
  玩家选回原字体也读不回来。
- ✅ 就地改那几处默认串，引擎自己会把默认项初始化成随包字体；玩家选了什么都原样透传。

**同一个默认串在 exe 里有好几份拷贝**（`.rdata` 字面量 + `.data` 全局初值 + 列表比对副本），
权威的那份是 **`lpDefault` 参数的地址**。改之前先 xref 找到调用点，不要按「名字一样就都改」猜；
全部改掉也无妨，但必须知道哪一处是决定性的。

> 抄期望字节时别信手写：不同编码的空格、全角/半角差异会让校验反复不过。
> 期望字节一律从文件里**读出来**再写进代码。

## 7. 代理 DLL 的构建

32 位目标需要 32 位工具链（`i686-w64-mingw32` 或 `x86_64-w64-mingw32-gcc -m32` + `ld -m i386pe`）。
不依赖 CRT 与导入库的做法：自行解 PEB 取 kernel32 导出表，再 `GetProcAddress` 其余函数。
若工具链不产 `.reloc`，两个 DLL 的基址必须显式给且不冲突。
