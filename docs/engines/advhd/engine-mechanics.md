# 引擎机制与逆向发现

本文档记录 AdvHD.exe 的脚本 VM 结构、图层槽机制、文本编码路径与语言包机制。文件格式见 [file-formats.md](file-formats.md)，指令集见 [ws2-opcodes.md](ws2-opcodes.md)。

## WS2 脚本 VM

在明文的观测样本 `AdvHD.exe`（内嵌 PDB 路径形如 `…\VAdvHD-1.99a\…\AdvHD_S.pdb`）中定位到脚本 VM 的完整结构，并在另一部作品的脱壳 exe 中逐项核对同构。**opcode 就是原始字节，直接作为分发表下标**：

| 环节 | 某作 exe（明文样本） | 另一作 exe（脱壳后） |
|---|---|---|
| handler 表 | `obj + 0x1B18` | `this + 0x1BA4` |
| 注册 | memset 0x400 后逐项写 handler（151/255 项） | 同构 |
| VM 主循环 | `sub_481450` | `sub_4727B0` |
| 操作数解析 + 格式表 | `sub_4F0A10` + `off_5EE2A8` | `sub_4CD400` + `off_55AEB8` |

- handler 表与格式表都**按原始 opcode 字节索引**；格式表每项指向以 `0xff` 结尾的类型码串（类型码 → 字节数见 [ws2-opcodes.md](ws2-opcodes.md)）。
- 上述地址是**各作 exe 的实测观测值，跨作需重验**；结构跨作同构，地址不同。
- 反汇编器与引擎表的比对结论：字节合计处处一致（全语料零错位）；差异仅在**指令分解**——引擎按变参格式表切分（`2e`/`66`/`0f`/`0e`/`05`/`13` 是引擎多指令、反汇编器合并或反之的典型），需要精确 opcode 计数的场景要注意。

**方法论红线**：某部语料的操作数取值统计只能当旁证；字段是不是绝对偏移、读几个字节，要读该 opcode 的格式表与 handler 定案（自身 exe 优先，其次同引擎明文样本）——「值看起来像偏移」不等于「引擎会照它跳」。

## LAYER_ORDER：图层槽登记表

### 文件格式

LAYER_ORDER 是一个 `.ws2` 文件，但不是可执行剧情脚本，而是**纯键名数据表**：

```
0x3f <count u8> <key0>\x00 <key1>\x00 ... <keyN>\x00 0x05 0xff 00...
  │              └────── 键名列表 ──────┘              └── 终止符
  └= 键数量
```

`0x3f` 就是引擎的 LayersList 指令；尾部 `05 ff …` 是引擎的「音效全停」，说明这个文件是当作普通脚本加载执行的，只是它只做「登记」这一件事。脚本里出现的 `04 LAYER_ORDER` 是 RunFile 子调用——每个立绘/背景块都显式跑一遍这张登记表。

### 性质：登记既有键，不定义键

**槽位本身由引擎内部硬编码**（`insertPNARefLayer` 等 Lua 绑定函数的注册表），LAYER_ORDER 只登记引擎已经认识的键。实测把表里加一个引擎不认识的新键（裸键或三元组）**永远注册不上**。⇒ LAYER_ORDER 里没有位置、没有坐标，也没有「新增槽位」的能力；它是白名单，不是布局表。

各作槽位清单不同（某作为 `ev` 单事件槽 + 19 键，另一作为 `ev01`/`ev02` 双事件槽 + blink/talk 三元组 + 114 键），以本作 LAYER_ORDER 内容为准。

### 引擎封装

引擎在绑定事件 CG 的 PNA 时，会按 PNA 内部的帧组结构自动生成 `ev01/ev01blink/ev01talk` 这类子图层——blink/talk 是引擎「封装」出来的，不从任何脚本显式调用；LAYER_ORDER 中的 blink/talk 键对应 PNA 为口型/眨眼动画提供的帧组数量。

## 事件 CG 槽对 PNA stem 的 7 字节硬限制

`ev01`/`ev02` 事件 CG 槽对 PNA 文件名（不含 `.pna` 后缀的 stem）有**严格的 7 字节（ASCII）硬限制**，某作 A/B 实测定性：

- stem ≤ 7 字节：可以注册（`HIK_17L`、`TEST_7B` 等）。
- stem > 7 字节：**必然失败**（报「サブレイヤー [ev01] は存在しません」）。
- 但 **`st*` 立绘槽无此限制**：15 字节的 Shift-JIS 名（如 `ORG_Aひかり_01M`）正常工作。

失败样本的共同点是 stem 字节数 > 7，与是否有前缀、PNA 内容、图层数、LAYER_ORDER 配置均无关 ⇒ 机制是 ev01/ev02 槽内部使用**定长 7 字节缓冲区**存储 stem，`st*` 槽用更大的缓冲。

命名应用：事件 CG 必须用简短名（不能加占 4 字节的隔离前缀），原版新增 CG 用 9X 段位（`[路线]_9X[L/S]`）；立绘可任意长名并可加隔离前缀。**资源注册失败优先怀疑资源名**，用「换成普通新名」的 A/B 测试最快定性（比继续逆向二进制高效得多）。

## 文字渲染路径：字体装载 + backlog 硬编码膨胀边

### 字体装载

脚本侧 `LegacyGame_utf8.lua` 定义 `g_fonts` / `g_fonts2` / `g_fonts3` 三组 `{name, file, CharSet}`，`file` 指向 `Fonts.arc` 内成员（槽名 `FOT-MatissePro-M/B.PTF` 之类，换字体只换槽内内容），由 `LegacyGame.lua` 调 `CLegacyFontInfo:extention(归档, 成员, 族名, charset)` 装载（`getGameEngineVersion() >= 1.4` 才生效，`g_fonts2` 另需 `getLangPatchFlag()`）。**归档名不在 `ArcFileName.lua` 的分派表里，也不是引擎写死的**：它是该调用点的明文常量（WillPlus 系为 `'Fonts.arc'`，exe 中无此字符串），所以理论上可以改；只是长度一变就要重写整块 147 KB 字节码的全部偏移，而语言包放同名归档即可达成同样效果 ⇒ 优先选后者（成本权衡，不是引擎限制）。native 侧 `sub_4F4EF0` → `sub_4591E0(a3=归档, a4=成员, a5=族名, a6=charset)` → 取流包装 → `CArchiveFile2`（与资源同一四级链，裸文件开关 `a5=0` ⇒ 裸目录层对字体不生效）。装载链：

1. 按槽名从 `Fonts.arc` 读出 PTF blob；
2. 解压（见 [file-formats.md](file-formats.md)「PTF 字体」：头 4 字节大小 + LZSS + XOR，ring 写指针从 1 起，窗内存密文）；
3. `AddFontMemResourceEx` 注册到**进程字体表**；
4. 之后 `add('system','Txt01'/'Name01', family, size, ...)` 走 GDI `CreateFontIndirectW` + `lfCharSet=GB2312_CHARSET` 按族名匹配（**族名匹配与系统字体无关**——字体自包含）。

工具：`galrev.advhd.ptf`（编解码，xor_key 从该作 `GameInfo.lua` 查）。

### backlog 图层的二次膨胀边（硬编码）

创建 backlog 的文本图层时，某作字体/文本层装载字体（`sub_4986A0` @ `0x498918`/`0x4989DE`）**无条件执行** `mov dword ptr [esi+4],1`（info+4 = 1，硬编码、不走参数）——据此渲染管线把文字字形外侧先绘一层 **1px 膨胀边缘**，再把原字形叠上，形成**二次绘制**。

该机制只影响字体管线，**不**变更内容；细笔画字体（日文明朝体系）在「1px 边缘叠加 + 原色叠合」下与背景「融」在一起产生肉眼可见的重影；笔画粗度足以使膨胀边缘与原字形对齐的字体（如思源黑体）在该层不再产生可见差异。**改字体**是不动引擎补丁的根治路线。

## 文本编码路径

`AdvHD.exe` 内建 BIG5 / GB2312 / SHIFTJIS / UTF-8 四种代码页，并提供 Lua 侧转换绑定（`MyConv__lua_utf8tosjis` / `MyConv__lua_sjistoutf8` / `lua_utf8split` 等）。

- 引擎内部对**脚本内窄字节文本按 CP932 解码**：对明文样本统计 `MultiByteToWideChar` 调用点的代码页参数，CP932 占绝对多数（40 处，UTF-8 仅 2 处）。
- 更严格的实测（两部作品的全 `.text` 扫描 + 运行时确认）：窄→宽的裸码页**只有 `932` 与 `65001` 两个值**，**没有 `936`/`950` 立即数**，且唯一入口把 `932` 写死在调用点、`setlocale` 也固定 `Japanese_Japan.932` ⇒ "内建四种代码页"只是 Lua/字体层的字符集常量，**不是**文本解码可选项；需要 UTF-8 内联文本时只能从 API 层改（做法见 [localization.md](localization.md)「不走 lng 的文本：码页 hook」）。
- **Lua 字符串层是 UTF-8**：`LegacyGame_utf8.lua` 里的非 ASCII 字符串就是 UTF-8 编码且直接传给引擎 API。
- 反方向 `WideCharToMultiByte` 以 UTF-8 为主——那是输出方向（交给 Lua / Steam API）。

**结论**：脚本内窄字节（如 `%LC` 这类标记与其后的名字）受 CP932 限制，简体专用字写不进去；**文本汉化必须走宽字符通路**——正文/选项走 `.lng`（UTF-16LE），人名走 `NameTable.txt`（UTF-16LE），剧本 ws2 字节不动。这也是官方简中的做法（见 [localization.md](localization.md)）。

## 语言包（≥1.9）：目录、选择与激活

引擎支持语言包：`AdvHDLang.dll`（语言桩，内含设置界面的本地化字符串与语言列表）加语言子目录。官方简中的目录结构：

```
<游戏根>/
└── zh-CN/
    ├── AdvHDLang.dll
    ├── Fonts.arc          # 含汉字字形的字体
    ├── Rio.arc            # .lng（正文/选项）+ NameTable.txt（人名）
    ├── Script.arc         # 仅 ui_language.lua（语言开关）
    └── SysGraphic.arc     # 系统界面图（如有汉化）
```

**识别与按成员覆盖**

- 判据是「子目录里存在 `AdvHDLang.dll`」（`PathFileExistsW`）；目录名即语言标识，标准 locale 名（如 `zh-CN`）会映射成系统显示名，其它名字原样显示。
- 引擎读某归档时**优先取包内同名成员**，缺失的成员回落根目录（实测：包内 `Rio.arc` 只放 1 个成员也能生效）⇒ 语言包只装**差异成员**即可；包内归档**必须与根目录同名**（主剧本归档若叫 `RIO1`，包里也要叫 `RIO1`）。
- `Script.arc` 同样按成员覆盖，所以包里放改动过的 Lua 即可（官方简中只放 1 个 `ui_language.lua`）。
- 中文剧本**没有 ws2**：剧本仍用原 ws2，中文全部经 `.lng`（正文/选项）与 `NameTable.txt`（人名）注入。无语言子目录的游戏，把它们放进主 `Rio.arc` 也可行，但是否完全等效需实机验证。

**选择语言：注册表**

- 所选语言存 `HKCU\Software\WillPlus\AdvHD\LanguageSettings`，**值名 = 游戏安装路径**，值 = 语言目录名。
- 值名是**安装路径经系统 ANSI 代码页转换**的结果：非当前 ACP 的字符变 `?`（`†` 在 GBK 系统上就是 `?`）。写这条注册表必须复刻同一规则，否则引擎读不到。
- **值为空 = 默认（英文）**，语言包整体不生效；没有任何语言包时，启动设置界面把默认语言显示为 English（即使原版是日文）。放好语言包后设置界面才出现语言下拉。

**激活：Lua 侧开关**

引擎**不按名调用**这些符号（exe 里没有对应字符串），它们由 `Script.arc` 里的 Lua 互相消费：

| 符号 | 作用 |
|---|---|
| `ui_language.lua`（放在语言包内，原游戏同名文件不要改） | 语言开关的定义处 |
| `getLangPatchFlag()` | 决定多语言特性是否启用、用哪套字体/文件：`1`=繁中、`2`=日文（多数原版默认）、`3`=简中、`0`=不启用；个别官中返回 `true`（下游全是 Lua 真值判断）。字体没生效时先查它 |
| `setInitLang()` | 置 `g_altLanguage = true`；`getAltLanguage()` 返回它，`getFontName()` 据此选 `g_fonts2` 槽（见 [localization.md](localization.md)「字体」） |
| `GameInfo.lua` 的 `getEnglishTitle()` | 引擎**按名调用**取语言无关标题；缺失则退回原名 |
| `LegacyGame.lua` 的 `g_SetDefaultLangJP` | **旧版**总开关：为 `true` 时多语言不激活（需改 `false`）；新版已移除该变量 |
| `Sys_c_*` / `Sys_*` 资源前缀 | **旧版/部分官中**在中文模式下请求带前缀的资源（包里需有同名 pna，或在 Lua 里统一前缀）；新版无此约定，走同名图层覆盖 |

引擎**能读未编译的 Lua**（可直接把明文 `.lua` 塞进 `Script.arc`）；语言开关 Lua 的字节码是定制 Lua 5.3（见 [file-formats.md](file-formats.md)「定制 Lua 5.3 字节码」）。

**`AdvHDLang.dll` 是什么**

- **纯资源 PE32**（i386、无导出、只有 `.rsrc`）：`RT_STRING` 若干条（设置界面与语言名的英/日两套）+ manifest；引擎 `LoadLibraryW` 加载它、用 `FindResourceW`/`LoadStringW` 读字符串。
- 替换/自造时**资源树必须由资源编译器重建**（`windres` 编 `.rc` 再链接）。手工把原 `.rsrc` 节搬到别的 RVA 会让节内偏移失效，`LoadStringW` 直接访问违例 —— 外在表现是**设置界面文字全空**，而 DLL "看起来"能加载。重建后须用 `LoadStringW` 逐条与原件比对。
- 这张 DLL **只在选中该语言时加载**，所以挂在它里面的代码（如码页 hook）天然是"语言包作用域"；工具见 `galrev.advhd.langdll`（重建资源 + 编译 + 校验）与 `galrev.advhd.langpack`（注册表/包发现/按成员合并视图）。

## 归档解析：四级链与可扩展槽位 ★

### 四级链（`CArchiveFile2` 构造）

每条「归档名 + 成员名」读取都走同一个构造函数 `sub_4D54F0(this, ebp, 归档名 a3, 成员名 a4, 裸文件开关 a5, 根目录 a6)`。`a3 != nullptr` 时按固定顺序尝试，**某一层一旦打开成功就不再往下走**（成员查不到也算打开过）：

| 层 | 路径 | 命中语义 | 成员缺失时 |
|---|---|---|---|
| 0 裸文件目录 | `<归档名去扩展名>\<成员名>`（相对**进程当前目录**，盘符/目录部分被丢弃） | 仅 `a5 != 0` 才探测；`_wfindfirst64i32` 命中即独占 | 继续第 1 层 |
| 1 用户数据根 | `<Path>\<归档名>` | 打开即**独占整归档** | **不回落**（资源直接失败） |
| 2 语言包目录 | `<语言包>\<归档名>` | 按成员查（软覆盖） | 关掉该归档，继续第 3 层 |
| 3 游戏根目录 | `<cwd>\<归档名>` | 基准归档 | 失败，返回空流 |

各层判据：

- **第 0 层的 `a5` 是各调用点的编译期常量，不是数据字段**。实测取值：`.ws2` 脚本加载 = **1**（`0x4CD1B7 push 1`）；标准位图层（`0x33` 的 CG/背景、图层分发器 case 4）= **0**；PNA（case 2 与直读路径）= **0**；`.mos` 模型 = **0**；**仅图层分发器 case 13** 传 1（`0x49BE88 push 1`）。⇒ 裸目录只对脚本与特定图层类型开放，**对 CG/PNA/模型一律关闭**；想用裸目录覆盖 CG 必须改 exe 的立即数，纯数据无法开启。
- `sub_4D2BB0`（图层从流构造）虽然把 `*(this + 0x2F0)` 当裸文件开关传给 `sub_4D2330`，但该字段来自**图层数据流**，只服务「从存档/图层流恢复」的路径；`0x33` 走 `sub_4D2230` + `sub_4D2330`，不经过它。`sub_4D7C90`（`a5 = v78`）的开关同样来自数据流，但其所属路径是**网络/序列化流**（同函数内有 `InternetCloseHandle`），与本地归档解析无关。
- **第 1 层是 HTTP 下载缓存，不是补丁位**：其实现是 `HttpSendRequestExW` / `InternetWriteFile` / `HttpQueryInfoW` / `InternetReadFileExW`，落盘目标直接拼在 `<Path>` 上；另一处用 `<Path>` + `&offset=` 拼分片名。该层整包独占、成员缺失不回落，只适合「下载一整份新归档」。**它会压过语言包层与根目录层**，且不受语言选择影响，所以任何补丁方案都必须把它视为禁用位。
- **`<Path>` 的构成**：`SHGetSpecialFolderPathW(csidl=26)`（`CSIDL_APPDATA`）+ 厂商标识 + 游戏英文标题，逐级 `wmkdir`。厂商标识与标题都来自 `Script.arc` 的 Lua（`GameInfo.lua` 的 `getAppInfo()` 与 `getEnglishTitle()`），**会把编译期默认值覆写掉**；因此 `<Path>` 的实际取值随游戏变化，必须以运行期实测目录为准，不能照抄某个作的值。
- **第 2 层是唯一「按成员覆盖 + 回落」的层**，`<语言包>`（含尾部 `\`）以**相对路径**解析，通常就是游戏目录下的语言子目录。它的 TOC 缓存键是**完整路径**，而第 1/3 层用**裸归档名**，所以两层同名归档的偏移表不会互相污染。
- **第 2 层只在语言包被启用时存在**：注册表值若为空串，`<语言包>` 不含目录名，该层整体失效。

### 归档名由 Lua 决定：`ArcFileName.lua`

引擎**不写死归档名**：每次「按资源名取归档」都问 Lua。入口是 `sub_444430(ctx, selector, out, slot, file)`，它经 `lua_getglobal` 按 selector 选函数、`lua_pcallk` 调用，取返回值后经窄→宽转换（`MultiByteToWideChar(932)`）作为归档名参数送进下游（图形走 `sub_4D2330`，音频走 `sub_4D8910`），最终到 `sub_4D54F0`。

**调用约定（两个实参的位置与语义，这是最容易搞错的地方）**：

```c
sub_444430(ctx, selector, &out, slot, file)   // selector: 0=Sound, 1=Graphics, 2=Model
                                              // 编译器逆序求值 ⇒ Lua 的 R0 = slot, R1 = file
lua_getglobal(L, "getSoundArcFileName" | "getGraphicsArcFileName" | "getModelArcFileName")
lua_pcallk(L, /*nargs*/ 2, /*nresults*/ 1, ...)
```

即**四个分派函数里 `a` = 槽名、`name` = 文件名**。两个参数都传，但**不同函数必须看不同的那个**：

| 函数 | 分派依据 | 依据为什么是这个 |
|---|---|---|
| `getRioArcFileName(name)` | 文件名 | **只传 1 个实参**（`sub_444220` 里 `push 1` 即 nargs=1） |
| `getGraphicsArcFileName(a, name)` | **文件名 `name`** | 图形资源名自带类型前缀（`evcc`/`bgcc`/`sys_`） |
| `getModelArcFileName(a, name)` | 无分派，恒返回模型归档 | — |
| `getSoundArcFileName(a, name)` | **槽名 `a`** | 见下 |

**音频为什么要按槽名分派**：槽名已经在音频播放指令里做完分类（`1e` 的槽是 `bgm01`、`28` 的槽是 `se01` / `charMIK` / …），而文件名不带类别信息，且**同一个文件名会被多个槽共用**（某作实测：`SE016.OGG` 被 4 个槽共用，共 70 个文件名跨槽共用）。按文件名分派等于把 3 类资源×N 个槽压成 1 个桶。

**`getSoundArcFileName` 的分派顺序与兜底**（语料里出现过的槽名族）：

| 分支 | 归档 |
|---|---|
| `<角色名>SysVoice`（`charMIKSysVoice` 等，角色名表逐项 `string.find`） | 系统语音归档 |
| `char` → | 语音归档 |
| `bgv` → | 音效归档 |
| `bgm` → | BGM 归档 |
| `systemvoice` → | 系统语音归档 |
| **兜底** | **音效归档，不是系统语音归档** |

⚠️ 兜底这一条容易写错且症状隐蔽：系统语音归档通常只装菜单试听音（某作 12 条 `*_SAMPLE.ogg`），任何落进去的音效都是静音的。

**槽名有引擎侧伪造来源**：音频侧至少有一处调用点压入**引擎自己合成的常量槽名**而不是脚本操作数（某作 `0x4719E5` 压入 UTF-16LE `"systemse"`，`selector=0`；地址是单作观测值，跨作需重验）。⇒ 不能假设槽名集合等于语料里出现过的槽名，分派逻辑必须能处理未预期的槽名（走兜底）。

要点：

- **字体归档不在这张表里**：字体由引擎用固定名字加载，**无法**通过 Lua 重定向。⇒ 「全局生效」的设计里字体只能整体替换根目录归档，不能走槽位。
- **返回值不受白名单约束**：任意归档名都会被接受并进入四级链（实测：把事件 CG 指向一个全新归档名后 CG 正常显示）。这是槽位机制成立的前提。
- 映射**不做缓存**，每次取资源都会重新调 Lua ⇒ 槽位探测的开销必须小。

#### 失败语义随资源类型而异（关系到「写错了会怎样」）

同一条「归档里查不到成员」的失败，在不同资源上表现完全不同，这是排障时最重要的对照：

| 资源 | 载入路径 | 成员缺失时 |
|---|---|---|
| 事件 CG / 背景（`0x33` 硬载入） | 图层贴图加载 | **空流 → 卡死无响应**，不报错 |
| **音频（BGM / 音效 / 语音）** | `sub_4D8910` | **静默跳过、返回 0，游戏继续跑** |

⇒ 映射表分派错误在图形上是「卡死」（显眼），在音频上是「静音」（极易漏测）。音频侧的回归不能只靠「游戏能启动」判定。

### 通用槽位：第三方补丁的接入点

在四个分派函数前插入**成员级槽位探测**，即可让第三方补丁以「放下一个归档」的方式接入，不改引擎、不注入、不用安装器：

```
<游戏根>\patch.arc     优先级最低
<游戏根>\patch2.arc
<游戏根>\patch3.arc    优先级最高（后注册优先）
```

语义：槽位只提供它想替换的成员，未命中回落原生归档。

必需条件（由四级链推导，缺一不可）：

- **必须做成员级查找，不能无条件返回槽位名**。引擎在**同一个请求名**上依次试第 0/1/2/3 层，**不会**把槽位名还原成原名再试。若对一个槽位里不存在的成员返回了槽位名，结果是最后在根目录的同名归档里查不到 → 空流 → `0x33` 卡死。实测：只含 1 个成员的槽位归档与完整归档并存时，槽位命中的成员显示替换内容，其余成员正常回落。
- **探测必须只读 TOC 区**：成员表之后是成员数据，整文件子串搜索会被数据里的字节序列假命中。
- 槽位名与语言包无关，因此槽位**对任何语言模式一视同仁**；跨语言生效的内容不应放进语言包目录。
- **用户数据根必须视为禁用位**（见上），否则会压过槽位并让回落失效。

实现形态：`luaL_openlibs` 已在 `WinMain` 调用，故 `io` / `string`（含 `string.unpack`）可用；启动时读一次各槽位归档的 TOC 并缓存，命中返回槽位名，否则返回原生名。引擎走 `luaL_loadbufferx`，**明文 Lua 可直接放进归档**，无需字节码编译器。

与语言包的关系（重要）：槽位只解决**归档名解析**。`ws2` 与其 `lng` 译文是**同一逻辑单元** —— `lng` 按脚本槽位/消息下标替换文本，脚本结构一变译文必然错配。⇒ **`ws2` 与其 `lng` 必须同一作者、同一版本、同一作用域提供**；优先级规则**不能**用于在两者之间仲裁，因为它不是同名成员谁赢的问题，而是成员间配合的问题。推论：只替换与脚本无关的资源（CG、语音、BGM、UI 图）的补丁与语言包天然同步，可安全走槽位；**修改 `ws2` 的补丁必须自带对应 `lng`**。

## 逆向与实测的经验

- **复刻官方映射表时，用字节码反汇编定案，不要凭字段名猜**：`getSoundArcFileName(a, name)` 两个形参都在，但只有 `a` 有分派意义；按参数名语义（「资源名」= 文件名）直觉推断会写错，而且错后**音频静音而不报错**。把原函数 `luac53.load()` + `luadis53.dump()` 出来，看它到底 `MOVE R5 := R0` 还是 `R1`，比读逆向伪代码更直接——伪代码的形参名是逆向工具猜的。
- **验证语料要盖到全量**：拿全语料的每条资源请求逐条跑「规则 -> 归档名 -> 该归档里真有这个成员吗」这一链，命中率一眼见底。典型偏差不是「找不到一个成员」，而是**整类资源同时失效**（命中率退化成只剩一个分支）——单看「游戏能启动、BGM 正常」发现不了。
- **失败表现按资源类型分档**：图形/背景缺失 = 卡死（显眼、必被发现），音频缺失 = 静音（隐蔽）。⇒ 改动归档名解析后，渲染路径可以抽查，**音频路径必须逐类验证**。
- **实测优于逆向的场景**：资源注册失败、显示效果一类问题，先做 A/B 测试（快、结论确定）；「资源在槽上注册失败」优先怀疑资源名/身份。
- **逆向不可替代的场景**：文本编码路径（统计 `MultiByteToWideChar` 代码页参数）与名字表机制（从官方语言包对照规则）这类结论，静态分析比逐个试错快且确定。前提是找到一份**未加密的同引擎 exe**；`.text` 加壳的游戏其 `.rdata`/`.data` 仍是明文，格式表可读，壳可脱（脱壳后熵与函数序言密度同明文样本量级）。
- **符号缺失**：无符号 C++ 二进制，函数名以 RTTI 形式存在（`.?AVCPNALayer@@`），Lua 函数注册表运行时按名/哈希动态绑定，无法经字符串 xref 静态定位函数体。
- **先找同引擎的官方样本，但拿到自身样本就先用自身**：同引擎样本给的是假设（枚举、门控、取值域可能与本作不同），自身样本才能定案；这条红线贯穿 [ws2-opcodes.md](ws2-opcodes.md) 与 [pna.md](pna.md)。
