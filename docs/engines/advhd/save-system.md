# 存档系统（CCST 快照链）与指定位置存档生成

本文档覆盖 AdvHD（MoeNovel 系）引擎存档格式的逆向结论与指定位置存档生成思路。工具：`galrev.advhd.saveadv`（只读解析）、`galrev.advhd.savegen`（生成）。块结构、字符串扫描与环序结论经数据驱动验证（全部真实存档零例外），**涉及 exe 地址与块内偏移的值是某作实测，跨作需重验**。

## 存档目录布局

存档目录在 `%USERPROFILE%\Saved Games\MoeNovel\<英文标题>\`。

- 主文件 `Save%03d.<标题>Save-MoeNovel` 是一串首尾相接的 CCST 块，无文件头；第 0 块为当前状态，物理 1..N-1 为按时间旧→新排列的历史环形缓冲（上限 251 块，环满覆写最旧）。
- savepoint 截图是独立的同名 PNG（116×65，可缺失）；槽位由引擎枚举磁盘文件获得，无索引文件。
- 伴随文件：`Save000`（全局小状态快照）、`Save000Favorite`（240 槽收藏位图，全 FF 为空）、`Save000GS`、`Resume.*`（最近读档）、`MessageFlag.dat`（逐脚本既読位图，格式见下）。

## CCST 块结构（小端）

- `+0x00`：魔数 `CCST`。常量不在 exe 内——由 `GameInfo.lua` 的 `getAppInfo` 第 4 字段（4 字符串）提供，引擎初始化器（某作 exe 地址 `0x417760`，跨作需重验）启动时读入全局。
- `+0x04`：tick（u32）。单位未确证；**跨游戏进程会归零**，同一存档的历史链里可含多次进程重启造成的回落，不能当全局时间轴，也**不要**当文件偏移用（同一场景内 tick 的跨度远大于该场景脚本体积）。
- `+0x08`：16 字节零（两个长度为 0 的字符串位：注释/章节名）。
- `+0x14`：对白文本长（UTF-16 码元数）。
- `+0x18`：对白文本（UTF-16LE，经 lng 与 NameTable 渲染后的最终显示文本）。
- 其后：引擎运行时对象图。无统一结构，各运行时对象虚序列化自己——图层参数（f32 坐标/缩放）、E-mote 状态、消息历史（每条 5 个字符串字段）、变量表、旗标位图、场景资源名等；脚本名出现在消息历史条目内，不是独立字段。

块内所有字符串均为 `[u32 长度][UTF-16LE 内容]`。可辨认的对象/频道名有 `%Message%`、`%Select%`、`%LC<人名>`、`bg01`、`bg02_ANIME`、`bgm01`、`st03`、`system`、`@ANIMATION_KEY`、`@STQUAKE_KEY` 等；资源以「归档名 + 成员名」成对出现。

块的组织：第 0 块 = 保存时的当前状态，第 1..N-1 块 = 回溯历史（旧→新）。物理顺序**不等于**时间顺序：只有按环序 `1,2,…,N-1,0` 读，tick 才严格单调递增——文件是一个环形缓冲，第 0 块是最后写入（最新）的那一格。

## PC 字段（位置恢复）

- **位置**：对象图起点（`0x18 + 对白文本长×2`）+ `0x410`（某作实测，跨作需重验）处的 u32。
- **语义**：ws2 解析游标 `<< 8`（低字节恒 0）。游标是引擎在 ws2 流中的原始解析位置，保存时停在「当前消息显示完、下一条显示指令已预解析」处；读档后从游标继续顺序解析，停在并显示后续消息。
- **写入规则**：跳到目标消息（`0x14`/`0x2e` 显示指令，偏移 `off`）→ 写 `(off + 3) << 8`（3 = opcode 1 字节 + id 2 字节；引擎恢复时读完指令头即显示该消息）。
- **验证**：全部真实存档低字节 = 0 且游标落在对应脚本范围内，0 例外；生成档实机验证落在目标场景、无卡顿、后续游玩正常。
- 图起点到 PC 字段之间（0x410 字节）为引擎固定布局，不随场景变化；场景相关的对象（图层、资源表等）在 PC 字段之后。

### 加载失败的表现

存档数据不完整或被改坏时，解析器从内部字段读出垃圾计数 → `std::vector` 扩容巨额分配 → `std::bad_alloc`（未捕获 → CRT 固定文案弹窗或直接闪退）；垃圾值可分配但解析不收敛则表现为卡死。截断/重排实验中同一文件结局不稳定，源于解析越界读到堆内存。

## MessageFlag.dat（逐脚本既読位图）

存档目录下的 `MessageFlag.dat` 保存**每个脚本的「已读消息」位图**。它是**记录的串接**，
无文件头、无结尾标记（读取循环以「偏移 < 文件长度」为界）。

记录格式（记录长度 = `len(名)*2 + 6 + A`）：

```
脚本名（UTF-16LE，NUL 终止）
u32 A = 8 + 位图字节数
u32 B          （计数：见「写位」的分支）
u32 Y          （位图首 4 字节的副本）
u8  位图[A-8]  （每消息 1 bit）
```

- **位图容量由 `A` 给出，不来自本文件**：引擎在**加载脚本**时从脚本文件**末尾 8 字节的明文尾表**
  （`[u32 消息数][u32 选项条目数]`）按 `(消息数 + 选项条目数 + 7) / 8` 分配。见
  [file-formats.md](file-formats.md)「WS2 脚本格式」。⇒ 记录里那个计数（`B`）是**已标记次数**，
  **不是消息总数**（旧口径把它误读成消息数，已更正）。
- 引擎侧缓存对象（某作实测，跨作需重验）：脚本加载时把记录插进一个 `std::wstring` 键的缓存；
  节点布局 = `+0x18` 位图 `std::vector`、`+0x24` 计数、`+0x28` 位图首 dword。
- **写位**：`bitmap[idx >> 3] |= 1 << (idx & 7)`，`idx` = 消息下标；**该函数不做边界检查**
  （某作 exe 地址 `0x4B6330`，只读版 `0x4B63E0`；跨作需重验）⇒ 位图容量小于脚本实际消息数时，
  高的下标直接写到堆上。
- 写入侧：只有**位图非空**的记录才落盘；**进程崩溃时不会写回**（正常退出才重写）——崩后该文件
  可能消失或留着上一次正常退出的内容，不能当作运行中内存态。
- 手改容量**不持久**：引擎按脚本尾表重建容量（改大的记录会在下一轮正常退出时被写回）。

### 越界写与崩溃表现

容量不足时写位落在相邻堆块上 ⇒ 延迟到某次 `free`/分配才被堆校验抓到 ⇒ `0xc0000374`（EventLog 报
`ntdll.dll` 的 `RtlReportHeapCorruption`，**不是**崩在写位处）；是否立刻致命取决于堆布局 ⇒ 表现为
**概率性**闪退。

**指纹**：`B > 8×(A-8)` 且位图全 0 —— 越界写不落地（每次读到的都是同一片野字节），同一下标被反复重标、
计数一路涨，位图保持 0。

**跨作验证**：记录格式在两部同引擎作品的 `MessageFlag.dat` 上整条解析成立（21 条 / 1703 B、
5 条 / 528 B，零残字节）；同签名崩溃亦见于未打补丁的官方作品（一条记录位图 384 位而 `B=393`）。

**触发条件**：位图容量只取决于「脚本尾表」与「脚本实际消息数」是否一致 ⇒ **任何让消息数变化而不更新
尾表的改动**（插入 / 删格 / 拆格 / 换脚本）都会把引擎推到位图不足的路径上。

## 读档路径上的 LNG

读档路径会调用 LNG 文本池加载（某作 exe 地址 `0x402930`，跨作需重验），`.lng` 的 XOR 密钥同样来自 `GameInfo.lua`（`getHostInfo` 的数字字段 → 全局字节，某作观测值 `0x2C`）。密钥机制见 [file-formats.md](file-formats.md)「LNG 文本容器」。

## 指定位置存档生成（galrev.advhd.savegen）

思路：以一份**同脚本**的真实存档为种子（seed），改写第 0 块的 PC 字段，使引擎读档后恢复在目标消息处。

1. 用 `list_messages` 枚举目标脚本全部可跳消息（按显示指令在 ws2 流中的出现顺序编号）。
2. 目标消息偏移 `off` → 写 `(off + CURSOR_HEADER) << 8` 到种子第 0 块的 PC 字段。
3. 写盘后回读校验 PC 字段已落盘且块数不变；同参数重复运行产出相同文件。

限制：目标脚本必须与种子存档当前脚本一致（引擎「当前脚本」标识的存储点尚未逆向，跨脚本移植待解）；跨脚本跳转的权宜做法是先用引擎在目标脚本里存一份档作种子。

**标定参数**：`PC_REL`（默认 `0x410`）与 `CURSOR_HEADER`（默认 `3`）是某作 exe 的实测值，**跨作需重验**；`save_dir` / `save_name` / `rio_arc`（脚本池归档路径）与 .lng 的 XOR 密钥必须按该作实际值传入。本模块的写盘函数**不要**对真实存档目录做测试调用。
