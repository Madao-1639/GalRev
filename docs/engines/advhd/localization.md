# 汉化通路

本文档覆盖 AdvHD 引擎游戏的文本汉化方案：lng 位置对应、说话人名、语音通道、字体与注入工程注意事项。格式细节见 [file-formats.md](file-formats.md)，编码路径与语言包目录见 [engine-mechanics.md](engine-mechanics.md)。

## lng 位置对应：严格等式

- lng 中**没有 id 字段**：引擎按播放顺序把第 N 条文本替换为第 N 条目。
- **严格等式：`lng 条数 == 0x14 指令条数 + Σ(0x0f 的 count)`**——`0x14` 与 `0x0f` 的**每个条目**各占一个槽位（一张选项表的 count 个条目各占一槽，strid 即槽位序），不是整张表占一槽；占位行（`%N`/`%P` 纯标记格）同样消耗条目。
- 引擎的替换对象是**最终显示文本**：对白长度按渲染后的文本计。
- ⚠️ 位置对应意味着 ws2 的对话流一旦增删，其后所有 lng 条目全部错位——就地插入内容后，宿主的配套 lng 必须**整体重建**；同理，新增 `0x0f` 会增加槽位数，必须同步补上对应文本，否则严格等式被破坏。
- 每个含文本的 ws2 都应有配套 lng；无 lng 的 ws2 应全部是无文本的系统/动画脚本（核对口径：其 `0x14` 计数为 0）。

## 说话人名：不经 lng，走 NameTable

- 说话人名（`0x15` 的 `%LC<英文名>` 前缀）**不经 lng 替换**——条目数核对证明 lng 只覆盖 `0x14` 正文与选项文本。
- 人名走引擎的名字替换表 `NameTable.txt`（UTF-16LE，任意简体字可写，完全绕开脚本内窄字节的 CP932 限制）：引擎拿 `%LC<英文名>` 查表，命中即替换为表右列。格式与「表键必须等于脚本标记」规则见 [file-formats.md](file-formats.md)「NameTable.txt」。
- 名字框是「继承」语义：`0x15` 只对它后面第一条 `0x14` 生效；插入段落发完必须恢复现场（重发进入时那条名字框），否则紧随的原始格会张冠李戴。
- 名字替换是否生效可用存档验证：存档第 0 块的名字框文本（`galrev.advhd.saveadv.name_label`）就是引擎要画进名字框的字符串，无需进游戏截图。

## 官方简中注入范式

官方简中语言包的做法（可直接复用，结构见 [engine-mechanics.md](engine-mechanics.md)「语言包目录」）：

1. 剧本 ws2 字节**完全不动**；中文全部经 `zh-CN/Rio.arc` 里的 `.lng`（正文/选项）与 `NameTable.txt`（人名）注入。
2. 字体换成含汉字字形集的 Fonts.arc，Lua 侧 `CharSet = GB2312_CHARSET`。
3. 系统界面图按 PNA 同名图层替换（见 [pna.md](pna.md)「写回」），不动 Lua、不改脚本引用。

## 语音通道规则

- Steam 侧自带的语音：通道 = `char` + 语音文件名前 3 字母（如 `MIK_0686.OGG` → `charMIK`），全语料零反例——这条规则可安全用于该侧语料的任何通道推导。
- 原版侧语音名前缀是**日文名首字母**（如 `MSA`=見里、`FYU`=冬子），与 Steam 通道名（`charMIS`/`charTOU`）不是同一个字母序列——**不能套规则，必须查表**（按说话人与语音前缀的逐句配对建立映射表）。
- 同一「配音来源」的多个前缀共用一个通道（同一声优的不同角色是同一音量桶），通道表按声源分组而非按角色。
- 语音与台词严格绑定：录音紧邻它那一句，插入/删格时该格的语音指令（`0x2e 28`）必须随格迁移或删除，否则语音会「漂」到下一格。
- 原版语音补入 Steam 侧时注意采样率：两版语料各自内部统一但互不相同（某作 Steam 全 48000、原版全 44100），导入语音需统一重采样对齐（`.soundlevel` 是按秒的包络，与采样率无关，不受重采样影响）。

## 字体

- PTF 容器内部（`[u32 大小][纯字面量 LZSS 混淆（XOR）流]`，XOR 密钥与 lng 同源，见 [file-formats.md](file-formats.md)「PTF 字体」）**可直接自制**——零 match 的 LZSS 与引擎解压端语义严格一致，零错排风险；但需跑**实机验证**（族名 + CharSet）。

- **族名接线**（改 `Script.arc` 内 `LegacyGame_utf8.lua` 的 Lua 字节码常量）：`g_fonts`（正文/backlog/整页）、`g_fonts2`（菜单族名选择器）、`g_fonts3`（人名框）。**族名必须与字体内部 Windows family name（name 表 id1/4/16 中的任意一条）逐字一致**；族长度**不**允许「家族名+风格」合写。族名替换**写进 `Script.arc` 的 Lua 字节码**一次后即定稿；后续流水线只**复制**该归档（**不**重复提升替换层级）。

- **字体格式**用 TrueType（magic `00 01 00 00`）而不是 CFF OpenType（`OTTO`）：GDI 的 `lfCharSet=GB2312_CHARSET` 过滤器对 CFF 匹配失败，TrueType 通路可正确匹配。

- **简体显示通路**：`CharSet = GB2312_CHARSET` 是简体渲染的关键；用 TrueType 源 + 自备字体的组合可**完全自包含**运行（玩家零字体安装，不需依赖系统字体）。

- **防字体渲染「重影」**：backlog 层创建函数**硬编码**给该图层开启二次膨胀边绘制（文字字形外侧先绘一层 1px 边界再叠原色）。细笔画字体（如日文明朝体）在背景下会"融"入背景产生肉眼可见的重影；笔画粗度足以使边缘膨胀后与原字形对齐的字体（如思源黑体）在该层不再产生可见差异。见 [engine-mechanics.md](engine-mechanics.md)「文字渲染路径」。

工具：`galrev.advhd.ptf`（编码 / 解码）+ fontTools 子集化（字体源 TTF → 按需裁剪）。

## 注入工程注意事项

- **文本替换必须逐字节 NUL 前缀精确匹配**：`dec.replace(b'\x00' + old, b'\x00' + new)`；裸字符串替换会命中已改名文件的尾巴，产生双前缀。
- **资源名编码是 Shift-JIS**（不是 UTF-8）；带日文的资源名必须 `name.encode('shift_jis')` 处理。
- **中文是翻译产物，不在脚本原文里**——不要尝试把中文编码成 Shift-JIS（会抛 `UnicodeEncodeError`）；中文文本只在 lng/NameTable 等 UTF-16LE 载体中搜索与写入。
- 资源名大小写：Arc 内成员名保留原始大小写，检索时统一 `.upper()`/`.lower()` 后比较（引擎对文件名大小写不敏感）。
- 跳转/引用提取必须按指令匹配（如 `\x07<名>\x00`），不能裸字符串搜索——正文或注释里可能出现同名串。
- 凡字节增删：`0x01`/`0x02`/`0x06` 的绝对偏移重定位与四条强不变式自检（见 [steam-achievements.md](steam-achievements.md)）不可省略；`0x14`/`0x0f` 槽位数变化后必须重建 lng（见上「位置对应」）。
- 幂等与回读：脚本补丁必须可重复运行（已满足则跳过），改写后必须回读验证。

## 不走 lng 的文本：码页 hook

`0x8f`（语音 + 字幕行）/`0x90`（字幕文本）这类**既不在 lng 池里、又在 ws2 内联**的文本，只能以窄字节存在，而引擎对脚本内窄字节的**解码码页是写死的**：全 `.text` 扫描只有 `932` 与 `65001`，没有 `936`/`950` 立即数，唯一入口把 `932` 写死在调用点，`setlocale` 也固定为 `Japanese_Japan.932`。所以"引擎内建 BIG5/GB2312/SHIFTJIS/UTF-8"只存在于 Lua/字体层的字符集常量，**不是**文本解码可选项。

**先排除数据层**（否则会白写 DLL）：目标文本换 UTF-16LE / UTF-8 / GBK 各试一次都是乱码、而 cp932 日文正常 ⇒ 解码固定；文本清空会回落到同句 `0x14` 的 lng 文本，但**丢掉朗读行本身**；`lng 条数 == 0x14 条数 + Σ0x0f 条目数` 严格成立即证明它不在池里；想用相邻的"消息族"指令搬走文本时，**会崩的指令族不要硬塞**。

**做法一：换码页（按内容判定）** —— DllMain 里改宿主模块导入表的 `MultiByteToWideChar`，码页 `== 932` 时改用 `CP_UTF8`。必备两道保护：纯 ASCII 直接放行（两解等价，也省掉全部判断）、**非法 UTF-8 原样走 932**（否则安装路径里的 `†`＝CP932 `0x81F5` 这类串会被误判）。作用面是全部窄→宽转换，且往往要靠白名单收窄 —— 那是"译文一改就要重编 DLL"。

**做法二：位置门（按 opcode 判定，推荐）** —— 只在"解析指定 opcode 的操作数期间"换码页，与内容无关：

1. 用「opcode → 操作数格式串」表的**唯一使用者**定位操作数解析器；其特征是 `movzx` 取一字节当索引、再 `mov reg, ds:<格式表>[eax*4]` —— 那个字节就是 opcode，来自**第 N 个栈参数**。
2. 若该函数是 `__thiscall`（`this` 在 ECX），栈参数从 `esp+4` 起排；`[ebp+arg_8]` 说明 opcode 是第 3 个栈参数。
3. 挑一个**恰好整数条指令、无绝对地址/相对跳转**的 5 字节序言（`push ebp; mov ebp,esp; push -1` 是典型），trampoline 原样搬 5 字节再接 `E9` 跳回。
4. 入口写 `E9` 跳到包装；包装把 opcode 存进全局/线程变量，然后**用 `jmp` 进 trampoline**。
   ⚠️ **不能用 `call`**：多压一个返回地址会让函数按 `[ebp+8]` 取参整体偏移 4 字节，现象是"opcode 读成一个地址"（不是崩溃）。
5. **失败即放弃**：写之前 `memcmp` 校验目标字节，不符只记日志不 patch；RVA 可能因壳/版本失效，可加"全映像唯一字节模式"兜底，两者都不中就不要动。
6. hook 里仅当 `码页 == 932` 且"当前 opcode ∈ 目标集合"时用 `CP_UTF8`（并去掉 `MB_ERR_INVALID_CHARS`，避免非法序列把整串清空），其余原样透传。
7. **兜底门（可选）**：位置门装不上时退化为"构建期扫描语言包脚本自动生成的白名单"，两者互斥 —— 换版本/换加载器也不会失去功能。

**每作都要重新标定**：解析器 RVA/签名与序言字节、opcode 是第几个栈参数、`thiscall` 与否、要放行的 opcode 集合、映像是否可重定位（无 `.reloc` ⇒ 固定 imagebase）。**开销**：每次转换只多一次比较 + 一次 4 字节字扫描（纯 ASCII 早退），实测 +13 ns/次；渲染阶段为宽字符，每帧 0。**崩溃风险**只来自"搬错序言长度"和"用 `call` 进 trampoline"，两者都能在写盘前用字节核对与本地探针排除。底层可复用的只有"语言包 DLL 本身"的工具：`galrev.advhd.langdll`（资源重建 + 编译 + `LoadStringW` 校验）与 `galrev.advhd.langpack`（注册表与包视图）；hook 的具体实现属于各补丁自己的代码，不放进本库。
