# 跨引擎逆向方法论

本文收录与具体引擎无关的逆向工程结论，全部来自实际完成过的内容还原补丁项目的返工教训。做任何引擎的分析与改写之前先读一遍；各引擎卷中的具体判据（如 WS2 指令边界、PNA 写回不变量）是本文原则在那个格式上的实例化。

## 一、证据与判据

### 字节覆盖不构成正确性证明

反汇编器可以在错误的位置重新同步，输出看起来完全合理的指令流；自带发射器加自带解析器的互验是循环论证——两边共享同一个错误假设时，往返一致只会一致地错。字节模板一旦在文档里写错，下游实现会原样继承这个错误（错误被对称复制）。

对策是引入**与推导路径无关的独立锚点**：语义级不变量（如「图层盒宽高必须等于内嵌 PNG 的 IHDR」「跳转目标必须落在指令边界」「坐标必须落在引擎已知档位集合」）、与可独立观察的事实（图片显示位置、实机行为）对照。逐字节往返一致是必要条件，永远不是充分条件。

### 判据的可靠性先于数字大小

一个覆盖率 100% 但依赖未经检验配对方法的比对，不如一个抽样但配对方法扎实的比对。配对方法本身是结论的一部分：报告任何比对结果时必须同时报告「怎么配对的」，否则数字不可信。

### 同引擎样本用于提出假设，自身样本用于定案

跨作证据（同引擎其他游戏的 exe、语料、现成工具）可以高效提出假设，但不能当定案：同引擎不同作的指令语义门控、参数档位、资源键来源都可能不同（实例：条件指令的 mode 门控在两作语料中行为不同）。拿到目标游戏自身的样本（exe、脚本语料、资源）之后，一切结论必须回到自身样本上重新验证。「同引擎有现成结论」只是省去从零摸索，不是省去验证。

### 全区间扫描与统计的边界

任何「X 永远等于 Y」的偏移或字段假设，必须用全语料扫描所有可能位置来排除反例，不能只验证命中的例子。反过来，统计规律（某字段在语料中恒为某值）只能作为强提示，不能替代从引擎代码或行为得到的机制解释——二进制语义不能靠统计外推。「我没看到反例」不等于「不存在反例」；语料没覆盖到的分支（如某 opcode 只在特定场景出现）要如实标注「边界已定、语义未定」。

### 诚实记录不确定性

对已经确定边界但尚未确定语义的东西，文档里明确写「边界已定、语义未定」，而不是编一个顺手的解释。缺少的信息不猜测补全，保持现状并如实记录。

## 二、逆向作业方法

### 先找同引擎的明文样本

开工第一步是找同引擎已有游戏（最好是已脱壳或未加密的版本）作为参照：指令集 handler 表、操作数格式表、资源格式都可以先在明文样本上摸清，再回到目标 exe 验证。目标 exe 自身被壳保护时，先评估已知脱壳方案（如针对 Steam DRM 的通用脱壳工具），脱壳产物与明文样本逐项对照确认同构性。

### 静态与动态互证

反编译器的输出是线索不是结论（变量重建、类型推断都会产生假象）；关键结论用动态验证（调试器断点、实机行为、A/B 对比实验）落锤。实机验证优先级最高：逆向结论与实机行为冲突时，先怀疑逆向结论。

### 资源与文本审计的覆盖面

资源审计必须覆盖**全部**资源类型（图形、语音、脚本、字体），只审一种会漏掉「裸名资源也被阉割/改动」的情况。审计的比对基准必须是原始信源；拿已经被修改过的一侧当基线等于自比。同名不等于同内容：判断两份图形资源是否同源，可行口径是图层帧池比对（先解码再比），合成整图与逐图层配对都不可靠。

## 三、写回与补丁工程

### 第一道闸：往返回归

只读解析器的隐性错误假设，第一次写回时才暴露。任何格式解析器完成后，先做 `serialize(parse(x)) == x` 的全语料往返回归，再做语义不变量检查。注意往返一致只证明「切片无遗漏」，不证明「字段语义正确」——语义要用独立不变量另验。

### 绝对偏移是头号事故源

脚本格式里凡是以「文件内绝对偏移」为操作数的指令（条件、跳转、选项表条目），插入、删除、重排任何字节之后都必须全部重算；只改本次动过的位置必然漏。写回器必须配套：改动前后指令流的精确刻画（除预期变化外逐字节相同）、全部跳转目标落在指令边界、偏移变化量等于精确预期。任何往脚本插入字节的功能，收尾时都要对**全部**受影响脚本（不是只查本次改的）复查所有依赖绝对偏移的结构。

### 改动最小化与隔离

同引擎不同版本的资源即使同名，内容语义也可能不同（图层的 layer_id 是纯位置量，两版同名文件的图层含义可以对不上）——一律走命名空间隔离，禁止覆盖。新资源落到引擎白名单允许的命名段。对游戏内容的任何修改都要能回答「原版数据是什么」：原版数据是权威信源，技术兼容性允许的调整（改名、重定位）与演出修改要严格区分。

### 幂等与复跑

生成类工具必须幂等：运行前检查「已满足则跳过」，重复运行不产生额外改动。流水线复跑必须 0 处改动——复跑报出改动即说明某步破坏了自己的输入。改写资源引用用 NUL 前缀的精确替换（防止误命中短名、防止双前缀叠加），改完必须回读验证。

### 闸的次序与计数

校验闸按依赖次序排列：先只读校验，再写盘，再表与产物对照，最后全量验收。每道闸的通过消息必须带计数，计数为 0 即视为失败（「扫描了 0 个文件全部通过」不是通过）。机械判据只提供置信度，规则不能代替人对最终质量的判断；聚合指标不能用于判定内容质量。

## 四、工程卫生

- 资源名与脚本内文本按引擎实际编码处理（Shift-JIS 系引擎的资源名用 Shift-JIS）；中文等非编码范围字符不要尝试用引擎编码编码，直接在已解码的字符串上操作。
- 提取资源的正则若只认 ASCII 字符集，会静默漏掉含日文名的引用；匹配资源引用时用 `.lower()` 做大小写不敏感比较（归档内外大小写常不一致）。
- Windows 控制台默认 GBK：脚本输出配置 UTF-8 或只用 ASCII，否则打印日文/中文即崩。
- 派生缓存能不落盘就不落盘：能直读源文件就不要维护副本，副本与源漂移是隐蔽错误源。
- 归档表末的 null padding 会破坏哈希稳定性与幂等性：归档写盘后检查并规范化 padding。
- 关键文件改动前备份，改动后用 SHA256 校验；安装包/发布产物的元数据必须取自实际产物（成员顺序、哈希），不能取自中间状态。
